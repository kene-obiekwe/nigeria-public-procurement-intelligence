## 3. How to Reproduce

Run from the repository root, with the source file verified per `data/README.md`:

```bash
psql -h localhost -p 5433 -U postgres -c "CREATE DATABASE nocopo_db WITH TEMPLATE template0 ENCODING 'UTF8'"
```

```bash
psql -h localhost -p 5433 -U postgres -d nocopo_db -v ON_ERROR_STOP=1 -f sql/02_schema/00_draft_core_schema.sql
```

```bash
.venv/Scripts/python python/ingest/01_load_staging.py
```

```bash
.venv/Scripts/python python/ingest/02_reconcile_staging.py
```

The loader runs as a single transaction. It truncates `stg.*` first, so
re-running it is safe, and a failure leaves staging unchanged. It refuses to run
if the source checksum differs from the pinned snapshot.

## 5. Schema Changes Made for Lossless Loading (DDL v1.1 → v1.2)

The Phase 4 v1.1 DDL was executed with the changes below. Each one was needed
to load the source without loss or constraint failure. None changes an
approved design decision.

| # | Change | Evidence | Reason |
|---|---|---|---|
| 1 | All 5 monetary columns `NUMERIC(30,2)` → `NUMERIC(30,4)` | The source carries 4 decimal places; budget `22566000.0061` would have been rounded | Staging must not alter source values (Implementation Plan Phase 5: "safe, non-destructive type casting") |
| 2 | `stg.award_suppliers`: added `supplier_seq`; `UNIQUE (award_id, supplier_seq)` replaces `UNIQUE (award_id, supplier_id)` | 6 awards (releases 114047–114052) list the same supplier, `NG-BPP-62660`, 5 times each: 24 repeated entries | The old constraint would have rejected rows that exist in the source. All 17,441 entries are kept as published; how to handle them in analysis is a Phase 6 decision (§7) |
| 3 | DQ flag columns became `GENERATED ALWAYS AS (...) STORED` | — | The approved flag rules (DQ-03 to DQ-09, DQ-14, DQ-16) now live in SQL and cannot drift from the values they classify (SQL-first). Same column names, values and CHECK constraints. Date classes come from one function, `stg.fn_date_quality_flag()`. `party_flag` is set by the loader because it records a source fact: the parties array is absent. |
| 4 | `party_name`, `supplier_name` generated from `*_raw` (trim + collapse whitespace) | — | Standardisation is visible in SQL; the raw value is preserved alongside |

**Date handling:** every source date has the form `YYYY-MM-DDT00:00:00Z`. The
loader checks this before casting to `DATE` and stops on any other time part,
so the cast loses nothing.

## 6. Differences From Phase 4 Expectations

### 6.1 Party count: 124,530, not ~216,514

The Phase 4 figure was an estimate (about 2 parties per release). The measured
count matches the Phase 2 role counts exactly:

- 108,250 parties with roles `{buyer, payer, procuringEntity}`
- 16,280 with roles `{payee, supplier, tenderer}`

108,250 + 16,280 = 124,530. The estimate was wrong; the data is as expected.
Phase 4 §5.9 has been annotated.

### 6.2 Award–supplier relationship is effectively 1:1

Phase 4 justified the junction table with "6 awards have 5 suppliers". In fact
**every award has exactly one distinct supplier**. The 6 cases repeat the same
supplier 5 times. The junction table is kept: it is source-faithful and handles
a genuine multi-supplier case if a future export contains one.
