## 1. Phase 4 Objective

Design a defensible PostgreSQL relational model that transforms the complex OCDS
source structure into a relational analytical foundation while preserving:
source traceability, release history, OCID/process identity, all procurement
lifecycle stages, supplier identity, data-quality flags, analytical metric
eligibility, and future extensibility.

This document is the authoritative design reference for Phase 5 implementation.

---

## 2. Design Principles

1. **Evidence-driven:** Every table, key, and relationship is justified by
   empirical dataset inspection (108,277 releases, 98,866 OCIDs), not by
   theoretical OCDS schema documentation alone.

2. **Release-centric staging:** The staging layer preserves the source's
   release-centric structure. Each release is one row; nested objects
   (tender, awards, contracts) are extracted into child tables linked by
   release_id or their own globally-unique IDs.

3. **Non-destructive:** All 108,277 releases are retained. No releases are
   deleted. The analytical snapshot rule is implemented as a VIEW, not as
   physical deduplication.

4. **Flag-at-grain:** Data-quality flags are placed at the grain where the
   quality issue occurs (e.g., `award_value_flag` on the awards table,
   `tenderer_count_flag` on the tender table).

5. **Date flags per column:** Each date field gets its own quality flag column
   because different dates on the same record can have different quality
   statuses.

6. **SQL-first:** The relational model is designed for PostgreSQL analytical
   queries (CTEs, window functions, aggregations) without requiring
   Python or Power BI for core transformations.

7. **Three-layer architecture:** `stg.*` (staging) → `core.*` (dimensions) →
   `analytics.*` (views). This follows the approved 7-layer technology
   architecture (Layers 3→4→5).

## 3. Schema-Design Gate Answers

### 3.1 What constitutes a procurement process?

A procurement process is identified by its **OCID** (`releases[].ocid`).
One OCID = one procurement process. The dataset contains **98,866 unique OCIDs**
across 108,277 releases.

**Exception (v1.1).** 192 OCIDs carry two or more unrelated planning budget lines.
Each line has a different `planning.budget.projectID`, description and amount.
189 of these OCIDs consist only of planning-only releases. No `projectID` spans
more than one OCID (97,749 distinct projectIDs). OCID remains the process key
for every lifecycle metric. For planned budget only, the grain is
(OCID, projectID). See §6.

### 3.2 How do releases relate to that procurement process?

Each release is a published snapshot of a procurement process at a point in time.
One OCID may have 1 to 74 releases. 92,586 OCIDs have exactly 1 release; 6,280
OCIDs have 2+ releases (9,411 excess releases total).

Most multi-release OCIDs carry identical content under **different
release-local IDs** for nested objects. **v1.1 correction:** v1.0 stated that
the content is identical in all cases. Measurement shows it is not:

| Pattern (multi-release OCIDs) | OCIDs |
|---|---|
| Budget object differs across releases | **836** (611 with ≥2 distinct non-null amounts; 225 only because some releases lack a budget) |
| Budget identical across releases | 5,666 |
| Same projectID, budget amount revised across releases | 422 |
| ≥2 distinct projectIDs (unrelated budget lines) | 192 |
| Mixed tag sets across releases | 236 |
| ≥2 full-lifecycle releases | 465 |
| Award value or supplier differs across releases | 5 |
| Integer-latest release has no budget | 79 |

The choice of which release represents a process therefore changes the
results. The rule in §6 is designed around this.

**Critical finding:** Award IDs and contract IDs are NOT reused across releases
for the same OCID. In 554 multi-release OCIDs with awards in both releases, each
release carries a different award ID for the same logical award (same value, same
supplier). Zero OCIDs have the same award ID appearing in more than one release.

## 6. Release / OCID Strategy

### 6.1 Problem statement

One procurement process (OCID) may have multiple published releases. If we
naively join through all releases, monetary values and counts are doubled.

### 6.2 Strategy: Section-level process-snapshot rule (v1.1)

> **v1.1 revision, 2026-10-07.** The project owner approved the
> multi-project budget treatment on 2026-10-07. The full v1.1 rule is pending
> design review (§18). v1.0 selected one *whole release*
> per OCID ("most lifecycle tags, then highest `release_id`"). Testing against
> the raw data (`docs/phase4_1_snapshot_validation_report.md`) found three
> defects:
> (a) the text tie-break picks the wrong release in 1,508 OCIDs;
> (b) a whole-release pick can land on a release without a budget (20 OCIDs)
>     or on an older full-lifecycle release over a newer revision (3 OCIDs);
> (c) one-release-per-OCID drops unrelated budget lines in the 192
>     multi-project OCIDs.
> v1.1 returns to the **section-level** wording of the frozen Phase 3 rule
> (`phase3_metric_eligibility.md` §1.2: "the preferred release for each
> lifecycle section"). It also makes the ordering and the budget grain explicit.

**Ordering.** "Latest" always means the highest `release_seq`
(`release_id` cast to integer; in SQL, `ORDER BY release_seq DESC`, which is
equivalent to `release_id::INTEGER DESC`). Text ordering is never used.
`release_date` is **not** part of the ordering: it carries one identical
publication timestamp on all 108,277 releases (DQ-10), so it cannot break ties.

**Which budget value.** When a budget line's amount differs across releases,
M-P01 uses the amount from the **latest** release carrying that line. It does
not use the maximum or the earliest. In the 422 same-project revisions, later
releases record the revised figure. The maximum would bias totals upward, and
the earliest would ignore published revisions. M-P01's aggregation grain is the
budget line, recorded as Phase 3 correction **C-06**
(`docs/phase3_2_correction_log.md`).

**Selection, per OCID and per lifecycle section:**

| Section | Selected from | Grain of result |
|---|---|---|
| Planning budget | For each `(ocid, budget_project_id)`, the latest release with a budget | One row per budget line (97,749) |
| Tender | The latest release containing a tender | ≤1 row per OCID |
| Award + contract (+ implementation, suppliers) | The latest release containing an award. Its contract, implementation and suppliers come from **the same release**. | ≤1 award, ≤1 contract per OCID |
| Buyer, tags | The latest release overall (buyer); tags from all releases (M-E03 uses the highest stage across releases, as in Phase 3) | 1 row per OCID |

**Why the award and its contract come from the same release.** Every contract's
`awardID` refers to an award in its own release (0 exceptions). The latest
award release equals the latest contract release in every OCID where both
exist (0 exceptions). So the contract → award foreign key always stays inside
the snapshot.

**Multi-project OCIDs (budget only).** M-P01 sums the latest budget per
`(ocid, budget_project_id)`. OCIDs with more than one budget line receive
`multi_project_flag = 'MULTI_PROJECT'` (192 OCIDs) so the treatment is visible.
Treatment category: **TRANSFORM + FLAG**. No other metric changes: these OCIDs
are planning-only except 3.

**Measured effect on planned budget** (excluding DQ-06 EXTREME, NGN bn):

| Rule | OCIDs with budget | Total |
|---|---|---|
| v1.0 as written (text tie-break) | 97,514 | 93,768.8 |
| v1.1 section-level, per project | 97,557 | 93,827.8 |

The aggregate difference is small (+NGN 59.0bn, about 0.06%). It is concentrated in
specific entities, though, so it matters for entity benchmarking (M-P01 by buyer).

### 6.3 Implementation approach

The rule is implemented as **views over staging**, not as physical
deduplication. All 108,277 releases stay in `stg.*`.

- `analytics.vw_process_snapshot`: one row per OCID (98,866), carrying the
  selected release for each section (`tender_release_id`,
  `award_release_id`), `budget_line_count` and `multi_project_flag`.
- `analytics.vw_budget_lines`: one row per `(ocid, budget_project_id)`
  (97,749), the input to M-P01.

These views are specified here. They are built in **Phase 7** (analytical
layer), after the Phase 6 core validation gate (Gate B). The Phase 5 staging
load must reconcile to 108,277 releases.

**Rationale for VIEW over physical table:** A materialized view or physical
table would require re-computation on data changes and creates a duplication
risk. A VIEW is always consistent with the staging data and clearly
communicates that the snapshot is a derived analytical construct.

### 6.4 Critical finding: Award ID behaviour

Award IDs and contract IDs are globally unique across the entire dataset —
they are NOT reused across releases for the same OCID. In 554 multi-release
OCIDs with awards in both releases, each release carried a different award
ID (e.g., award `425` in release `2049` vs. award `1755` in release `6895`),
even though the award values were identical.

This means the process-snapshot rule effectively resolves the deduplication
problem by selecting ONE release per OCID. No separate award-level
deduplication logic is needed beyond the snapshot rule.

**v1.1 additions:**
- Of the 554 OCIDs with awards in more than one release, 549 repeat the same
  value and supplier. In the other 5, the latest release carries a later
  correction: a ×100 award value reverted (`ocds-gyl66f-521027024-000087`) and
  a placeholder supplier `'1'` replaced by a named supplier
  (`ocds-gyl66f-124004001-000772`). The latest-release rule is the defensible
  choice. These OCIDs are listed in the validation report §3.2.
- Each release has at most 1 award, so after the snapshot every OCID has at
  most one award. The multi-award case behind Phase 3.1 C-03 exists only across
  releases, and the snapshot resolves it. M-E02 keeps its single-award
  condition as a guard.
- In 1 OCID the latest tender release differs from the latest award release.
  M-E02 therefore takes the tender date and award date from their own sections.

## 7. Supplier Strategy

1. **Primary identity:** `supplier_id` from `parties[].id` for parties with
   a `supplier` role. This is the grouping key for all supplier analysis.

2. **No fuzzy matching:** Suppliers are NOT merged based on name similarity.
   DQ-13 documents that 1,483 supplier IDs map to multiple name variations.
   These are retained as-is.

3. **Incomplete IDs flagged:** Suppliers with bare `NG-BPP-` prefix lacking
   a numeric suffix receive `supplier_id_flag = 'INCOMPLETE'`. These are
   excluded from primary concentration metrics (M-S01) per Phase 3.1
   Correction C-02.

4. **Canonical mapping deferred:** The `dim_supplier_canonical` table
   (DQ-15) requires controlled human-supervised entity resolution.
   The table structure is documented in the DDL as a commented-out
   future extension. **Decision (2026-10-07):** core tables keep the raw
   source supplier attributes (`supplier_id`, `supplier_name_raw`). The
   mapping table is created no earlier than Phase 7, and only after an
   explicitly approved, human-supervised resolution step (a required human approval point).

5. **Name preservation:** Original source supplier names are stored in
   `supplier_name_raw` alongside any standardized version.

## 9. Monetary Modelling

- **Data type:** `NUMERIC(30,2)` for all monetary fields (supports values up
  to ₦999,999,999,999,999,999,999,999,999,999.99)
- **Currency:** Stored alongside each amount (uniformly NGN observed)
- **Source preservation:** Original values retained, never imputed
- **Zero handling:** Zero values retained and flagged `ZERO_VALUE` (DQ-16),
  never converted to NULL
- **Cross-stage independence:** No assumption that budget = award = contract.
  Each lifecycle stage has its own independent monetary fields
- **Double-counting prevention:** The section-level snapshot rule (§6.2)
  ensures one monetary value per OCID per lifecycle stage. Planning budget is
  the one exception: it has one value per (OCID, budget line).

---

## 10. Date Modelling

- **Data type:** `DATE` for event dates; `TIMESTAMPTZ` for release_date
  (publication metadata)
- **Source preservation:** Original date strings parsed to PostgreSQL dates
  with quality flags preserving the classification
- **Quality classification per date:**
  - VALID — plausible operational date
  - PLACEHOLDER — 2001-01-01 (DQ-08)
  - FUTURE — year 2026–2050 (DQ-09)
  - IMPOSSIBLE — year > 2050 (DQ-09, e.g., year 2922)
- **release_date (DQ-10):** All 108,277 releases share the identical value
  `2021-05-03T22:44:00Z`. This is package publication metadata, NOT a
  procurement event date. It must never be used for temporal analysis.
- **Chronological validation:** Duration metrics require end_date ≥ start_date;
  negative durations indicate invalid pairs to be excluded.

## 11. Implementation / Transaction Modelling

- **Source location:** `contracts[].implementation.transactions[]`
- **Expected rows:** ~13,617
- **No date field:** DQ-11 confirms transaction date is universally absent.
  The schema has NO `transaction_date` column.
- **Value semantics:** DQ-12 is UNRESOLVED — whether values represent
  cumulative progress or incremental disbursements is unknown. The schema
  stores raw values with a note that aggregation is deferred.
- **Design for future resolution:** The `transaction_value` column stores
  the raw source value. When DQ-12 is resolved, analytical views can
  apply the correct aggregation logic without schema redesign.
- **v1.1 evidence (does not resolve DQ-12):** 13,403 contracts have 1 transaction
  and 107 have 2. In 10,145 contracts the transaction values sum exactly to the
  contract value. 2,818 sum below it and 417 sum above it. Among the
  two-transaction contracts, the second value is equal to the first in 55,
  lower in 43 and higher in 9. That mix fits neither a clean cumulative pattern
  nor a clean incremental one. **Decision:** DQ-12 stays UNRESOLVED.
  M-I01 uses transaction *presence* only. No view sums transaction values.

## 12. Milestone Modelling

- **Source locations:** Two distinct locations in the JSON:
  1. `contracts[].milestones[]` (contract-level milestones)
  2. `contracts[].implementation.milestones[]` (implementation milestones)
- **Design:** Single `stg.milestones` table with a `milestone_source`
  discriminator column ('CONTRACT' or 'IMPLEMENTATION')
- **Volumes (v1.1):** 14,894 CONTRACT milestones and 27,960 IMPLEMENTATION
  milestones, 42,854 in total. v1.0 estimated about 27,960 in total.
- **Date quality (v1.1, measured):**
  - CONTRACT milestones have **no** `dueDate`/`dateMet` keys at all (14,894 / 14,894).
  - IMPLEMENTATION milestones: 10,895 have dates. 10,857 are VALID and 38 are the
    2001-01-01 PLACEHOLDER. 17,065 have no dates. None are FUTURE or IMPOSSIBLE.
  - `dateMet` equals `dueDate` in **every** implementation milestone. The two
    fields are not independent observations.
- **Decision:** Load both date columns as published, and classify their flags at
  load time with the standard DQ-08/09 classes. No approved metric uses milestone
  dates. Milestone slippage (dateMet − dueDate) is **not measurable** from this
  source and must not be presented as on-time delivery.

## 13. Normalization Decisions

| Decision | Rationale |
|----------|-----------|
| Planning as separate table | All 108,277 releases have planning; separate table avoids 20+ columns on releases and supports clean budget queries |
| Tender as separate table | Only 18,408 releases have tender; avoids 88% NULL columns on a wide releases table |
| Awards as separate table | Different grain (award-level) with own globally-unique PK; supports supplier junction |
| Contracts as separate table | Different grain with own PK; links to awards via awardID; hosts implementation sub-entities |
| Award-suppliers junction | 6 awards have 5 suppliers — many-to-many relationship requires junction |
| Single milestones table with discriminator | Both contract-level and implementation-level milestones share the same structure; discriminator column distinguishes origin |
| Parties as separate table | Multi-role, multi-release; normalized for supplier dimension extraction |
| Buyer/supplier dimensions in core | Avoid repeating entity names across every staging row; enable clean dimensional joins |
| No physical snapshot table | Process-snapshot rule is a VIEW — preserves all release history |
